# Воспроизведение с YouTube восстановлено

Дата: 2026-09-05 · заменяет вывод из `youtube-block.md`, который к этому
моменту устарел дважды.

**Решение: клиент плеера `visionos` вместо дефолтных, и извлечение ссылки
на телефоне, а не на сервере.**

---

## Что изменилось с 31 августа

Тогда вывод был «SABR, сделать нельзя ничего». Он был верен наполовину:
SABR действительно включён, но не для всех клиентов сразу.

| проверка 2026-09-05 | результат |
|---|---|
| 13 клиентов плеера с жилого IP | ссылку отдаёт **только `visionos`** |
| `visionos` + жилой IP (Алматы, Beeline) | **5 из 5** треков, отдача 206 |
| `visionos` + IP дата-центра (Oracle) | **1 из 4**, остальные — бот-проверка |
| WARP как прокси | мёртв: `Host unreachable` |
| прямые запросы с сервера без прокси | проходят, но с бот-проверкой |

Два независимых препятствия, которые раньше сливались в одно:

1. **SABR** — снимается выбором клиента. `visionos` на него не переведён.
2. **Фильтр по адресу** — снимается только сменой адреса. Жилой проходит,
   датацентровый нет.

## Почему извлечение уехало на телефон

Ссылку достаёт тот, кто будет по ней играть. Телефон сидит на обычном
мобильном или домашнем интернете и для ютуба неотличим от любого зрителя,
а сервер сидит на адресе Oracle и отклоняется.

Реализация: `mobile/src/api/youtube.ts`, 180 строк, без библиотек.

У клиента VISIONOS нет ни подписи, требующей запуска JS-плеера, ни
PO-токена, ни авторизации (`REQUIRE_JS_PLAYER: False`, `REQUIRE_AUTH: False`).
Поэтому весь протокол — два обычных запроса:

```
1. GET  https://www.youtube.com/            → visitorData из HTML
2. POST https://www.youtube.com/youtubei/v1/player?prettyPrint=false
        заголовок X-Goog-Visitor-Id + контекст клиента VISIONOS
        → streamingData.adaptiveFormats[].url, уже готовые
```

Без `visitorData` плеер отвечает `LOGIN_REQUIRED` — это единственная
неочевидная деталь, и именно на ней ломались прошлые попытки повторить
запрос вручную.

## Что осталось на сервере

`YTDLP_PLAYER_CLIENTS = ["visionos"]` в `backend/app/src/modules/songs/utils.py`.

Бэкенд остаётся откатом: телефон пробует сам, и только при неудаче идёт
к API. Работает примерно в четверти случаев — мало для основного пути,
достаточно для запасного.

Прокси WARP выключен (`profiles: ["proxy"]` в compose): он перестал
отвечать, а прямые запросы проходят не хуже. Если фильтр ужесточат,
поднимается обратно одной командой.

## Когда это снова сломается

Когда `visionos` переведут на SABR — а его переведут. Признак будет
характерный: `playabilityStatus.status = OK`, но `adaptiveFormats` без
ссылок и `serverAbrStreamingUrl` в ответе. Код это различает и говорит
«YouTube не отдал прямых ссылок на аудио», а не общее «не получилось».

Тогда нужно будет либо найти следующий непереведённый клиент (список
в `YTDLP_PLAYER_CLIENTS` заведён именно списком, чтобы дописать), либо
дождаться поддержки SABR в yt-dlp.

Вывод, который стоит запомнить: «сделать нельзя ничего» почти всегда
означает «нельзя тем способом, которым я проверял». Тринадцать клиентов
были перебраны, но `visionos` в yt-dlp появился позже той проверки.
