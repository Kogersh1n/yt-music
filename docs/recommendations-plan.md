а играется всё через `source: 'youtube'` — этот путь в приложении уже есть

## Да, профиль по авторам построить можно

Ты спрашивал, получится ли. Данных на это хватает с избытком:

| источник | что даёт | есть сейчас |
|---|---|---|
| 441 лайк из YT Music | автор + название + `video_id` | да, `/sync/wanted` |
| «радио по треку» | похожие к любому треку | да, без авторизации |
| локальные лайки | что нравится в самом приложении | `src/local/likes.ts` |
| счётчики прослушиваний | сколько всего играли | `src/local/stats.ts` |
| **события прослушивания** | **что, когда и докуда** | **нет — это и надо добавить** |

Профиль автора — это просто частота: сколько его треков в лайках, сколько
раз ты их включал, сколько дослушал. Ничего сложного, но считать не из чего,
пока нет последней строки.

---

## Чего не хватает: журнал событий

Сейчас `stats.ts` хранит агрегаты, а `recents.ts` — последние 20 треков без
отметок времени. Из этого нельзя получить ни «что я слушал в июле», ни
«какого автора я стал слушать чаще».

Нужна одна структура:

```ts
interface PlayEvent {
  trackId: string;
  youtubeId: string | null;
  author: string;
  title: string;
  startedAt: number;     // unix ms — по нему нарезаются месяцы
  seconds: number;       // сколько реально проиграло
  duration: number;      // сколько длится трек
  completed: boolean;    // дослушал или переключил
}
```

Она закрывает **обе** задачи сразу:

- **рекомендации** — `completed` отделяет «понравилось» от «пропустил через
  десять секунд», а `startedAt` даёт свежесть: то, что слушал вчера, весит
  больше того, что год назад;
- **рекапы** — месяц это просто фильтр по `startedAt`.

Объём смешной: тысяча событий в месяц по сотне байт — около мегабайта в год.
MMKV это не заметит. Хранить год-два, старое отбрасывать.

**Почему нельзя обойтись счётчиками.** Пропуск — самый сильный сигнал вкуса,
и он сильнее лайка: лайк ставят редко и вдумчиво, а пропускают честно и
не задумываясь. В `played` эта информация теряется безвозвратно.

## Что делаю я (оптимизация приложения)

### 1. `src/local/plays.ts` — журнал событий

По образцу существующих сторов: MMKV, `useSyncExternalStore`, синхронное
чтение. Пишет событие при смене трека и при остановке.

### 2. Подключение к плееру

В `usePlayback.ts` / `queueStore.ts` уже отслеживается позиция — событие
пишется там, где трек сменился. Важно фиксировать **фактически проигранное
время**, а не длину трека: иначе пропуск будет неотличим от прослушивания.

### 3. Главный экран

Сейчас `HomePage` показывает общую ленту. Разложить на секции:

```
Слушать снова      ← recents.ts, уже есть
Из твоих лайков    ← /sync/wanted, играется по youtubeId
Может понравиться  ← твоя рекомендательная логика
```

Первые две можно сделать сразу — данные уже есть.

### 4. Каталог лайков как источник треков

`/sync/wanted` отдаёт 441 трек с `video_id`. Приложению нужен из них
`Track` с `source: 'youtube'` — дальше плеер справится сам, ничего
скачивать не нужно.

### 5. Экран рекапа

Отрисовка готовых цифр. Считаются они из журнала событий, так что экран —
чистая вёрстка без логики.

## Что строишь ты (ранжирование)

Здесь я не лезу — это и есть интересная часть.

**Профиль автора.** Веса из трёх источников: лайки YT Music, дослушивания,
пропуски со знаком минус. Свежесть — множитель, затухающий со временем.

**Кандидаты.** «Радио по треку» на твоих топовых вещах даёт по 20-50 похожих
на каждую. Из 441 лайка — тысячи кандидатов.

**Оценка.** Совпадение кандидата с профилем: знакомый автор, часто
встречается в выдаче по разным твоим трекам, ещё не слышал.

Подсказка из того, что уже работает на сервере: в `/sync/recommendations`
оценка — просто частота появления кандидата в «радио» по разным твоим
трекам. Грубо, но работает. Твоя версия может добавить веса авторов,
свежесть и пропуски.

## Рекапы

Раз в месяц из журнала событий:

- сколько часов и треков
- топ авторов и топ песен
- новые авторы, которых не было в прошлом месяце
- самый активный день, любимое время суток
- «жанр месяца» — если тянуть жанры из YT Music

Считать **на устройстве**: данные там, сервер не нужен, работает офлайн.

Хранить не сам рекап, а срез: посчитал первого числа, сохранил результат
за прошлый месяц, события старше двух лет удалил.

**Тонкость:** первый рекап будет пустым — журнала ещё нет. Поэтому чем
раньше начнёт писаться `plays.ts`, тем раньше появится, что показывать.
Это единственная причина не откладывать первый пункт.

---

## Порядок

1. **`plays.ts` + подключение к плееру** — до всего остального: данные
   начинают копиться с этого момента и раньше не появятся
2. **Секции на главной** — «Слушать снова» и «Из лайков» работают сразу
3. **Твоя рекомендательная логика** — когда наберётся хотя бы пара недель
   событий
4. **Рекап** — когда пройдёт первый полный месяц

Первые два пункта — моя часть, могу сделать сразу. Третий твой. Четвёртый
осмысленно делать последним, но структуру данных под него закладываем
в первом.

# Задачи на бэкенд

Приложение уже пишет журнал и умеет считать рекап локально. Дальше нужен
сервер — иначе история умирает вместе с переустановкой приложения.

Порядок важен: первая задача разблокирует остальные.

---

## 1. Приём событий прослушивания

**Зачем.** Журнал сейчас только на телефоне. Снёс приложение — потерял всё,
и первый рекап опять считать с нуля. Плюс без событий на сервере нельзя
считать вкус там, где лежат остальные данные.

**Модель** `modules/plays/models.py`:

```python
class PlayEvent(Base):
    __tablename__ = 'play_event'

    user_id:    Mapped[UUID]        # FK user.id, ondelete CASCADE, index
    track_id:   Mapped[str]         # String(64) — 'yt:<id>' или UUID песни
    youtube_id: Mapped[str | None]  # String(20), index
    author:     Mapped[str]         # String(100), index
    title:      Mapped[str]         # String(200)
    started_at: Mapped[datetime]    # timezone=True, index
    seconds:    Mapped[int]
    duration:   Mapped[int]
    completed:  Mapped[bool]
```

**Ручка** `POST /plays/batch`, тело — массив событий, до 500 за раз.

**Обязательно — идемпотентность.** Телефон шлёт пачками и будет повторять
отправку при обрыве связи. Без защиты одно прослушивание запишется трижды
и перекосит весь профиль вкуса.

```sql
UNIQUE (user_id, track_id, started_at)
```

и вставка через `ON CONFLICT DO NOTHING` — тот же приём, что в лайках
(`songs/repository.py`). Ответ: сколько принято, сколько было дублями.

**Готово, когда:** отправка одной пачки дважды не меняет число строк.

---

## 2. Профиль вкуса по авторам

**Зачем.** Это вход для твоего ранжирования. Сервер отдаёт цифры, решение
принимаешь ты.

**Ручка** `GET /taste/artists?days=90&limit=50`

```json
[{
  "author": "...",
  "seconds": 14300,        // общее время
  "plays": 62,             // запусков
  "completed": 48,         // дослушано
  "completion_rate": 0.77, // ключевой признак вкуса
  "last_played": "...",    // для свежести
  "liked_tracks": 5        // сколько его вещей в лайках YT Music
}]
```

**Считать одним SQL-запросом**, а не выборкой событий в память:
`GROUP BY author` с `SUM(seconds)`, `COUNT(*)`, `SUM(completed::int)`.
При тысячах событий разница между запросом и обходом в питоне —
миллисекунды против секунд.

`liked_tracks` берётся из `ytmusic.liked_songs()` — совмещается по имени
автора уже в питоне, там счёт идёт на сотни.

**Готово, когда:** ручка отвечает быстрее 200 мс на 10 000 событий.

---

## 3. Каталог лайков

**Зачем.** `/sync/wanted` семантически означает «что надо скачать» и
отдаёт только недостающее. Приложению нужно «мои лайки» целиком —
их можно слушать, ничего не скачивая.

**Ручка** `GET /catalog?limit=100&offset=0`

Те же поля, что в `/sync/wanted`, плюс `in_library: bool` у каждого трека.
Пагинация обязательна: лайков уже 441, а список растёт.

**Заодно кэш.** `ytmusic.liked_songs()` ходит в сеть каждый раз, около
секунды. Положить в Redis на 15 минут — ключ `ytmusic:liked:{user_id}`.
Тот же приём, что с `ytstream:` для ссылок.

**Готово, когда:** повторный запрос отвечает из кэша, а `in_library`
верно отмечает уже скачанное.

---

## 4. Кандидаты без ранжирования

**Зачем.** Сейчас `/sync/recommendations` сам считает оценку по частоте.
Раз ранжирование пишешь ты, сервер должен отдавать сырые данные, а не
готовое решение.

**Ручка** `GET /candidates?seeds=20&per_seed=20`

```json
[{
  "video_id": "...",
  "title": "...", "author": "...", "duration": 0, "cover": null,
  "seeds": ["трек-источник-1", "трек-источник-2"]
}]
```

Ключевое отличие от текущей ручки: **`seeds` — список, а не число**.
Из него видно, от каких именно твоих треков пришёл кандидат, и ты сможешь
взвесить их по-своему: свежие тяжелее старых, дослушанные тяжелее
пропущенных.

**Осторожно с временем.** 20 источников по запросу к YT Music — это
20 сетевых походов, секунд десять. Варианты: `asyncio.gather` пачками
по пять, либо считать в celery и складывать результат в Redis.
Синхронно в ручке — только если источников мало.

**Готово, когда:** отвечает быстрее 5 секунд на 20 источниках.

---

## 5. Рекапы на сервере (потом)

**Зачем.** Приложение уже считает рекап локально из своего журнала —
этого хватает. Серверная версия нужна ради двух вещей: рекап переживает
переустановку и доступен, если появится второе устройство.

**Ручка** `GET /recap/{year}/{month}`

Те же поля, что в `src/features/recap.ts` — брать структуру оттуда,
чтобы приложение могло переключиться с локального счёта на серверный,
не меняя экран.

Считать одним `GROUP BY` с фильтром по месяцу, результат класть в Redis
до конца месяца: прошедшие месяцы уже не изменятся.

**Делать последней.** До неё нужен хотя бы месяц накопленных событий.

---

## Чего делать не надо

**Не переносить ранжирование на сервер.** Оно твоё, и на телефоне ему
удобнее: данные уже там, работает офлайн, эксперименты не требуют
передеплоя.

**Не хранить рекомендации в базе.** Они пересчитываются из профиля
и кандидатов — таблица под них устареет раньше, чем пригодится.
Redis с коротким сроком жизни достаточно.
