# Задачи на бэкенд: рекомендации и рекапы

Дата: 2026-08-31

Приложение уже пишет журнал прослушиваний и считает рекап локально.
Эти задачи переносят данные на сервер и дают тебе всё нужное, чтобы
написать своё ранжирование.

Порядок обязателен: первая задача разблокирует все остальные.

---

## Задача 1. Приём событий прослушивания

### Зачем

Журнал сейчас живёт только в MMKV на телефоне. Три следствия, каждое
неприятное по-своему:

- **Переустановил приложение — история обнулилась.** Первый рекап опять
  считать с нуля, профиль вкуса заново набирать месяцами.
- **Второе устройство не увидит ничего.** Планшет или новый телефон
  начнут с чистого листа.
- **Считать вкус негде.** Лайки YT Music и медиатека на сервере, события
  на телефоне — соединить их можно только там, где есть и то, и другое.

### Как поможет

Появляется единственная таблица, из которой считается **всё остальное**:
профиль авторов (задача 2), рекапы (задача 5), веса для твоего
ранжирования. Без неё задачи 2 и 5 просто не из чего делать.

### Как сделать

**Модель** — `modules/plays/models.py`:

```python
class PlayEvent(Base):
    __tablename__ = 'play_event'

    user_id: Mapped[UUID] = mapped_column(
        SQLUuid, ForeignKey('user.id', ondelete='CASCADE'), index=True
    )
    track_id: Mapped[str] = mapped_column(String(64), index=True)
    youtube_id: Mapped[str | None] = mapped_column(String(20), index=True, default=None)
    author: Mapped[str] = mapped_column(String(100), index=True)
    title: Mapped[str] = mapped_column(String(200))

    started_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), index=True)
    seconds: Mapped[int] = mapped_column()
    duration: Mapped[int] = mapped_column()
    completed: Mapped[bool] = mapped_column()

    __table_args__ = (
        # Ключ идемпотентности — см. ниже, это самое важное здесь.
        UniqueConstraint('user_id', 'track_id', 'started_at',
                         name='play_event_unique'),
        # Под запросы профиля: «события юзера за период, сгруппировать по автору».
        Index('idx_play_user_started', 'user_id', 'started_at'),
    )
```

Не забудь добавить модуль в `db/registry.py` — иначе alembic его не увидит
и миграция получится пустой.

**Ручка** — `POST /plays/batch`:

```python
@plays_router.post("/batch", response_model=BatchResult)
async def upload_batch(
    data: list[PlayEventCreate],
    session: SessionDep,
    user: UserDep,
):
    if len(data) > 500:
        raise BadRequestError("За раз не больше 500 событий")
    return await plays_service.ingest(session, user_id=user.id, events=data)
```

**Идемпотентность — главное требование.** Телефон отправляет пачками и
будет повторять отправку при обрыве связи: сеть на телефоне рвётся
постоянно, а подтверждение может не дойти уже после того, как сервер
записал. Без защиты одно прослушивание запишется трижды, и профиль вкуса
перекосится в пользу тех треков, которые слушали при плохой связи.

Приём тот же, что уже работает в лайках (`songs/repository.py`):

```python
from sqlalchemy.dialects.postgresql import insert as pg_insert

stmt = (
    pg_insert(PlayEvent)
    .values([e.model_dump() | {"user_id": user_id} for e in events])
    .on_conflict_do_nothing(constraint="play_event_unique")
)
result = await session.execute(stmt)
return {"accepted": result.rowcount, "duplicates": len(events) - result.rowcount}
```

Одной пачкой, а не циклом: 500 отдельных вставок — это 500 обращений
к базе вместо одного.

### Подводные камни

**Время.** Телефон шлёт `startedAt` как unix ms в UTC. Колонка
`timezone=True`. Если принимать naive datetime, значения разъедутся на
часовой пояс — и рекапы начнут показывать чужие дни. Принимай int
и переводи явно: `datetime.fromtimestamp(ms / 1000, UTC)`.

**Чужие события.** `user_id` берётся из `UserDep`, а не из тела запроса.
Иначе кто угодно сможет писать в чужую историю.

**Обрезка строк.** `title` у ютуба бывает длиннее 200 символов. Режь
на входе в схеме (`Field(max_length=200)`), иначе получишь
`DataError` на всю пачку из-за одного трека.

### Готово, когда

- Отправка одной и той же пачки дважды не меняет число строк в таблице.
- В ответе видно, сколько принято и сколько отсеялось дублями.
- Попытка записать событие с чужим `user_id` игнорируется.

## Задача 2. Профиль вкуса по авторам

### Зачем

Это **вход для твоего ранжирования**. Сервер отдаёт цифры, решение
принимаешь ты — так и договаривались.

Почему именно авторы, а не треки: у тебя 441 лайк, а исполнителей там
в разы меньше. По трекам статистика размазана и почти везде единицы,
по авторам она набирается быстро и уже через неделю о чём-то говорит.

### Как поможет

Даёт три сигнала, которых нет ни в лайках, ни в счётчиках:

- **`completion_rate`** — доля дослушиваний. Самый честный признак: лайк
  ставят редко и вдумчиво, а пропускают не задумываясь.
- **`last_played`** — свежесть. Вкус меняется; то, что слушал в июне,
  должно весить меньше того, что слушал вчера.
- **`liked_tracks`** — сколько вещей автора в лайках YT Music. Связывает
  историю прослушиваний с явными предпочтениями.

### Как сделать

**Ручка** — `GET /taste/artists?days=90&limit=50`:

```json
[{
  "author": "Molchat Doma",
  "seconds": 14300,
  "plays": 62,
  "completed": 48,
  "completion_rate": 0.77,
  "last_played": "2026-08-30T21:14:00Z",
  "liked_tracks": 5
}]
```

**Считай одним SQL-запросом**, а не выборкой в память:

```python
since = datetime.now(UTC) - timedelta(days=days)

stmt = (
    select(
        PlayEvent.author,
        func.sum(PlayEvent.seconds).label("seconds"),
        func.count().label("plays"),
        func.sum(func.cast(PlayEvent.completed, Integer)).label("completed"),
        func.max(PlayEvent.started_at).label("last_played"),
    )
    .where(PlayEvent.user_id == user_id, PlayEvent.started_at >= since)
    .group_by(PlayEvent.author)
    .order_by(func.sum(PlayEvent.seconds).desc())
    .limit(limit)
)
```

Разница не косметическая: на десяти тысячах событий `GROUP BY` в базе —
это миллисекунды, а тот же подсчёт обходом в питоне — секунды плюс
мегабайты в памяти.

`liked_tracks` добавляй уже в питоне поверх результата: `ytmusic.liked_songs()`
отдаёт сотни записей, свести их по имени автора — копеечная операция.

### Подводные камни

**Имена авторов не нормализованы.** YouTube отдаёт то `Bonobo`, то
`Bonobo - Topic`, то `Bonobo, Jordan Rakei`. Без приведения к общему виду
один исполнитель размажется по трём строкам. Минимум — обрезать
` - Topic` и брать первого из списка через запятую. Идеала тут не будет,
но 90% случаев это закроет.

**Ранжирование по секундам, а не по запускам.** Запуск легко накрутить
перелистыванием очереди; секунды — нет.

### Готово, когда

- Ручка отвечает быстрее 200 мс на 10 000 событий.
- В плане запроса виден `Index Scan` по `idx_play_user_started`,
  а не `Seq Scan` (проверяется через `EXPLAIN ANALYZE`).

## Задача 3. Каталог лайков

### Зачем

`/sync/wanted` семантически означает «что осталось скачать» и отдаёт
только недостающее. Приложению нужно другое: **вся библиотека лайков**,
которую можно слушать прямо сейчас, ничего не скачивая.

Плюс сейчас каждый вызов `ytmusic.liked_songs()` идёт в сеть — около
секунды на запрос. Открыл главный экран, свернул, вернулся — три секунды
ожидания на ровном месте.

### Как поможет

Главный экран получает секцию «Из твоих лайков» из 441 трека, которая
открывается мгновенно. В приложении под это уже есть `getLikedCatalog()`
в `src/api/sync.ts` — останется переключить путь.

### Как сделать

**Ручка** — `GET /catalog?limit=100&offset=0`:

```json
{
  "items": [{
    "video_id": "...", "title": "...", "author": "...",
    "duration": 218, "cover": "...",
    "in_library": false
  }],
  "total": 441,
  "has_more": true
}
```

`in_library` считается сверкой с `song.youtube_id` — тем же множеством,
что уже собирает `SyncService._downloaded_ids`.

**Кэш в Redis** — по образцу `ytstream:` из `songs/service.py`:

```python
key = f"ytmusic:liked:{user_id}"
cached = await redis.get(key)
if cached:
    return json.loads(cached)

liked = ytmusic.liked_songs(limit=1000)
await redis.setex(key, 900, json.dumps([asdict(t) for t in liked]))
```

15 минут — разумный компромисс: лайки меняются редко, а лишний поход
в сеть на каждое открытие экрана заметен.

**Пагинацию делай по кэшу**, а не запросом в YouTube на каждую страницу:
взял из Redis весь список, нарезал срезом. 441 запись в памяти — это
ничто, а походов в сеть станет один вместо пяти.

### Подводные камни

**Сброс кэша при изменениях.** Скачал трек — `in_library` у него должен
смениться. Либо удаляй ключ при добавлении песни, либо считай `in_library`
поверх кэша (список лайков кэширован, а множество скачанного берётся
из базы каждый раз). Второе проще и не рассинхронизируется.

### Готово, когда

- Второй запрос подряд отвечает быстрее 50 мс.
- `in_library` меняется сразу после скачивания трека, не дожидаясь
  истечения кэша.

## Задача 4. Кандидаты без ранжирования

### Зачем

Сейчас `/sync/recommendations` сам решает, что хорошо: считает частоту
появления кандидата в «радио» по разным твоим трекам. Это работает, но
**ранжирование пишешь ты** — значит сервер должен отдавать сырые данные,
а не готовый вердикт.

### Как поможет

Разделяет данные и решение. Ты сможешь менять формулу сколько угодно,
не трогая сервер: экспериментируешь в приложении, где данные уже есть
и передеплой не нужен.

### Как сделать

**Ручка** — `GET /candidates?seeds=20&per_seed=20`:

```json
[{
  "video_id": "...",
  "title": "...", "author": "...", "duration": 0, "cover": null,
  "seeds": [
    {"video_id": "...", "title": "Волны", "author": "Molchat Doma"},
    {"video_id": "...", "title": "...", "author": "..."}
  ]
}]
```

**Ключевое отличие от текущей ручки: `seeds` — список, а не число.**
Из него видно, от каких именно твоих треков пришёл кандидат. Дальше ты
взвесишь их по-своему: источник, который слушал вчера и дослушал,
весит больше того, что пропустил в марте.

Ту информацию, которая сейчас схлопывается в одно число `score`,
восстановить потом невозможно — поэтому её и надо отдавать целиком.

**Источники бери из профиля вкуса** (задача 2), а не случайные из
медиатеки: топ авторов по секундам даст более осмысленных кандидатов,
чем первые попавшиеся строки таблицы.

### Подводные камни

**Время ответа — главная проблема.** 20 источников — это 20 сетевых
запросов к YouTube Music по секунде каждый. Синхронно в ручке получится
20 секунд, что неприемлемо.

Три варианта, по возрастанию сложности:

1. **`asyncio.gather` пачками по пять.** `ytmusicapi` синхронный, поэтому
   через `asyncio.to_thread`. Двадцать источников уложатся секунды в четыре.
2. **Считать в celery, класть в Redis.** Ручка отдаёт последний посчитанный
   результат мгновенно, задача обновляет его раз в несколько часов.
   Кандидаты не портятся от того, что им пара часов.
3. Комбинация: если в кэше пусто — посчитать синхронно первые пять
   источников, а полный расчёт поставить в очередь.

Я бы начинал со второго: у тебя уже настроен celery beat, а свежесть
кандидатов с точностью до часа никому не нужна.

**Отсеивай уже известное.** Кандидат, который есть в лайках или в
медиатеке — не рекомендация. Фильтруй на сервере, чтобы не гонять
лишнее по сети.

### Готово, когда

- Ответ приходит быстрее 5 секунд (или мгновенно из кэша).
- В `seeds` у кандидата действительно несколько источников, когда он
  похож на несколько твоих треков.

## Задача 5. Рекапы на сервере

### Зачем

Приложение уже считает рекап локально — `src/features/recap.ts`,
и этого достаточно для одного устройства. Серверная версия нужна ради
двух вещей: **рекап переживает переустановку** и доступен на втором
устройстве.

### Как поможет

Тот же экран, но данные не пропадут. Приложение сможет переключиться
с локального счёта на серверный, не меняя вёрстку — если структура ответа
совпадёт.

### Как сделать

**Ручка** — `GET /recap/{year}/{month}`.

**Структуру бери из `src/features/recap.ts`** — там уже есть интерфейс
`Recap` с полями `totalSeconds`, `topArtists`, `newArtists`, `busiestDay`,
`favoriteHour`, `completionRate`. Повтори его один в один, тогда
переключение в приложении будет заменой одной функции.

Считается одним `GROUP BY` с фильтром по месяцу — тем же запросом, что
в задаче 2, только с границами периода вместо `days`.

**Кэшируй прошедшие месяцы навсегда.** Август 2026 больше не изменится:
посчитал один раз, положил в Redis без срока. Текущий месяц — на час.

### Подводные камни

**`newArtists` требует два периода.** «Новый» — это тот, кого не было
в предыдущем месяце. Значит нужен второй запрос за прошлый период,
и на первом месяце он вернёт пусто — все авторы будут «новыми».
Это не баг, но в интерфейсе первый рекап стоит подписать иначе.

**Часовой пояс.** `favoriteHour` считается в часах пользователя, а на
сервере время в UTC. Либо принимай смещение параметром, либо считай
этот показатель на клиенте — данных для него в ответе достаточно.

### Готово, когда

- Рекап за прошедший месяц отдаётся из кэша мгновенно.
- Цифры совпадают с тем, что показывает локальный расчёт в приложении.

## Чего делать не надо

**Не переносить ранжирование на сервер.** Оно твоё, и на телефоне ему
удобнее: данные уже там, работает офлайн, а эксперименты не требуют
передеплоя.

**Не хранить рекомендации в базе.** Они пересчитываются из профиля
и кандидатов. Таблица под них устареет раньше, чем пригодится — Redis
с коротким сроком жизни достаточно.

**Не удалять локальный журнал после отправки.** Пусть лежит на телефоне:
рекап должен открываться офлайн, а сервер — резервная копия, а не
единственное место хранения.

## Порядок и зависимости

```
1. События  ──┬─► 2. Профиль вкуса ──► 4. Кандидаты
              │
              └─► 5. Рекапы

3. Каталог — независимо, можно делать когда угодно
```

Первая задача блокирует три из пяти. Третью можно взять хоть сейчас —
она ни от чего не зависит и сразу оживит главный экран.
