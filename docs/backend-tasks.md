## Что было не так в прошлой версии

Я построил профиль **по авторам**: сложить секунды по каждому исполнителю
и рекомендовать похожих на топовых. Это не то, что ты просил.

И это правда хуже. Усреднение по автору теряет главное: если из десяти
песен исполнителя тебе нравится одна, а остальные ты пропускаешь, в его
средних цифрах это исчезает. А в журнале прослушиваний — видно.

Рекомендации строим **от конкретных треков, которые ты слушал**.

## Задача 1. Приём журнала прослушиваний

`POST /plays/batch`

### Зачем

Приложение уже пишет журнал (`src/local/plays.ts`): что включил, когда,
сколько проиграло, дослушал или пропустил. Но лежит он только на телефоне —
переустановил приложение, и всё пропало.

Журнал нужен для **обеих** твоих задач: из него берутся и семена для
рекомендаций, и цифры для рекапов.

### Модель

```python
class PlayEvent(Base):
    __tablename__ = 'play_event'

    user_id:    Mapped[UUID]        # FK user.id, CASCADE, index
    track_id:   Mapped[str]         # String(64): 'yt:<id>' или UUID песни
    youtube_id: Mapped[str | None]  # String(20), index — по нему ищем радио
    author:     Mapped[str]         # String(100)
    title:      Mapped[str]         # String(200)
    started_at: Mapped[datetime]    # timezone=True, index
    seconds:    Mapped[int]         # сколько реально проиграло
    duration:   Mapped[int]
    completed:  Mapped[bool]        # дослушал (>80%) или переключил

    __table_args__ = (
        UniqueConstraint('user_id', 'track_id', 'started_at',
                         name='play_event_unique'),
    )
```

### Единственная тонкость — идемпотентность

Телефон отправляет пачками и **повторит отправку при обрыве связи**.
Подтверждение может не дойти уже после того, как сервер записал.

Без защиты одно прослушивание запишется дважды, и трек, который ты слушал
в метро с плохой сетью, получит вес в два раза больше заслуженного.

Приём тот же, что уже работает в лайках (`songs/repository.py`):

```python
stmt = (
    pg_insert(PlayEvent)
    .values([e.model_dump() | {"user_id": user_id} for e in events])
    .on_conflict_do_nothing(constraint="play_event_unique")
)
```

Одним запросом на всю пачку, не циклом.

**Готово, когда:** отправил одну пачку дважды — число строк не изменилось.

## Задача 2. Рекомендации от прослушиваний

Правка существующего `/sync/recommendations`.

### Зачем

Сейчас метод берёт семена из медиатеки — то есть из скачанного. Но ты
ничего не качаешь, а слушаешь по ссылкам. Значит семена должны браться
из журнала.

### Что менять

В `SyncService.recommendations` заменить источник семян:

```python
# было: тракi из медиатеки
rows = await session.execute(
    select(Song).where(Song.youtube_id.is_not(None)).limit(seeds)
)

# стало: то, что реально слушал и дослушал, свежее первым
rows = await session.execute(
    select(PlayEvent.youtube_id, PlayEvent.title)
    .where(
        PlayEvent.user_id == user_id,
        PlayEvent.completed.is_(True),
        PlayEvent.youtube_id.is_not(None),
    )
    .order_by(PlayEvent.started_at.desc())
    .distinct()
    .limit(seeds)
)
```

Дальше всё как есть: для каждого семени запрашиваем «радио» через
`ytmusic.related_tracks()`, считаем, сколько раз встретился каждый
кандидат.

### Как улучшить оценку

Сейчас каждое семя весит одинаково. Осмысленные веса:

- **свежесть** — слушал вчера весит больше, чем месяц назад
- **сколько раз включал** — вернулся к треку пять раз, значит зацепило
- **пропуски со знаком минус** — если кандидат похож на то, что ты
  регулярно пропускаешь, опустить его

Это и есть та часть, которую ты хотел писать сам. Формулу не навязываю.

**Готово, когда:** в выдаче нет треков, которые ты пропускал, и есть
похожие на те, что дослушивал на этой неделе.
