# Синхронизация с YouTube Music

Дата: 2026-08-30

Сервер знает, что тебе нравится. Домашний компьютер это скачивает.
Телефон играет из хранилища.

---

## Почему так, а не через туннель

Была идея пробросить Tailscale до домашней машины и качать с сервера через
неё. От неё отказались: **если компьютер всё равно должен быть включён,
туннель не даёт ничего, а забирает многое.**

| | Tailscale | домашний воркер |
|---|---|---|
| компьютер должен работать | да | да |
| путь трафика | дом → сервер → R2 | **дом → R2** |
| настройка сети | VPN на двух машинах | нет |
| что качается дважды | всё аудио | ничего |

Туннель имел бы смысл ровно для одного: прослушивания по требованию через
дом. Для фоновой закачки он проигрывает по всем пунктам.

---

## Как устроено

```
YouTube Music ──► сервер: читает лайки и плейлисты (ytmusicapi)
                         │
                         ├─ сверяет с song.youtube_id
                         └─ GET /sync/wanted → чего не хватает
                                    │
домашний компьютер ◄────────────────┘
      ├─ yt-dlp скачивает со своего адреса (ютуб его пускает)
      ├─ PUT напрямую в R2 по подписанной ссылке
      └─ POST /songs/ регистрирует трек
                         │
                    телефон играет из R2
```

Ключевое: **блокировка перестаёт мешать**. Задержка не важна — никто не ждёт
у экрана. Компьютер выключен — очередь ждёт следующего запуска, слушать это
не мешает, музыка идёт из хранилища.

## Что добавлено на сервере

### `Song.youtube_id`

Новая колонка, миграция `66ecebf91fa5`. По ней синхронизация понимает, какие
треки уже скачаны. Nullable — у файлов, залитых вручную, идентификатора нет.

### `integrations/ytmusic/client.py`

Обёртка над `ytmusicapi`: лайки, плейлисты, поиск. Отдаёт только метаданные —
аудио отсюда не берётся никогда.

С файлом авторизации читает личную библиотеку, без него умеет только открытый
поиск и честно об этом сообщает.

### `modules/sync/`

| ручка | что делает |
|---|---|
| `GET /sync/status` | сколько лайков, сколько скачано, сколько осталось |
| `GET /sync/wanted` | список того, чего не хватает |

Обе под авторизацией. Проверено:

```
/sync/status  200 {'authenticated': False, 'liked_total': 0, 'in_library': 0, 'wanted': 0}
/sync/wanted  502 {'detail': 'YouTube Music error нет файла авторизации...'}
без токена    401 {'detail': 'Not authenticated'}
```

Без настроенной авторизации ничего не падает — `status` честно отвечает
`authenticated: false`.

### Попутно исправлено

`/songs/upload-cover-url` был объявлен как `SongCoverResponse` (`{cover_url}`),
а сервис отдаёт `{upload_url, file_key}`. Ответ не проходил валидацию, и ручка
падала при каждом вызове. Теперь `UploadCredentialsResponse`.

Это как раз та ручка, через которую воркер заливает обложки — без правки
синхронизация не заработала бы.

## Домашний воркер: `tools/home_sync.py`

Один файл без зависимостей кроме `yt-dlp`. Логинится на сервере, забирает
список, качает, заливает, регистрирует.

```bash
pip install yt-dlp

export YTMUSIC_API=https://ytmusic.82-70-63-136.nip.io
export YTMUSIC_EMAIL=твоя@почта
export YTMUSIC_PASSWORD=пароль

python tools/home_sync.py --once            # один проход
python tools/home_sync.py --watch 3600      # проверять раз в час
```

Что он делает правильно:

- **не перекодирует.** Берёт `bestaudio[ext=m4a]` как есть. Пережатие в mp3
  было самой долгой частью импорта, а качество от второго сжатия падает.
  m4a играет и на Android, и на iOS нативно.
- **обновляет токены.** При 401 меняет пару и повторяет запрос. Учитывает,
  что refresh одноразовый: если обмен не удался, входит заново.
- **не падает на одном треке.** Ошибка — пропуск и переход к следующему.
- **обложка не критична.** Не сохранилась — трек всё равно попадёт в медиатеку.

## Режим списка: работает уже сейчас

Файл авторизации нужен только для чтения твоих лайков. Если просто знаешь,
что хочешь скачать — достаточно JSON со списком названий:

```json
[
  "GONE.Fludd Мамбл",
  "Kavinsky Nightcall",
  "Bonobo Kerala"
]
```

```bash
python tools/home_sync.py --from-json tools/wishlist.json
```

Названия превращаются в идентификаторы роликов через поиск YouTube Music,
**а он работает без авторизации**. Проверено: три запроса из трёх нашлись.

Повторы отсеиваются на сервере по `song.youtube_id` — один трек дважды
в хранилище не попадёт.

## Что нужно от тебя: файл авторизации YouTube Music

Без него сервер не видит твои лайки. Получается так:

```bash
pip install ytmusicapi
ytmusicapi browser
```

Команда попросит вставить заголовки запроса из залогиненного браузера:
открой music.youtube.com, DevTools → Network → любой запрос к `/youtubei/` →
Copy → Copy request headers. Получится `browser.json`.

Дальше на сервер:

```bash
scp browser.json ubuntu@82.70.63.136:/opt/ytmusic/secrets/ytmusic.json
ssh ubuntu@82.70.63.136 \
  'echo YTMUSIC_AUTH_FILE=/run/secrets/ytmusic.json >> /opt/ytmusic/.env'
```

И смонтировать файл в `docker-compose.prod.yml` рядом с `cookies.txt`.

**Важно:** это заголовки для чтения библиотеки, а не для плеера. Блокировка
дата-центра сюда, скорее всего, не распространяется — поиск с сервера
работает. Но проверить это можно будет только с настоящим файлом.

## Рекомендации

Работают **без файла авторизации**: «радио по треку» — публичная выдача
YouTube Music. Проверено, отдаёт 49 похожих на одну песню.

```
GET /sync/recommendations?seeds=15&limit=30
```

Как считается: для каждого трека из медиатеки спрашиваем похожие и
считаем, сколько раз каждый кандидат встретился. **Частота и есть оценка** —
если песня оказалась похожей сразу на несколько твоих, она вероятнее
попадёт во вкус, чем случайная из выдачи по одной.

В ответе есть `because_of` — название трека, с которого началась цепочка,
чтобы рекомендация не выглядела взявшейся из ниоткуда.

### Ночное пополнение

Задача `sync_recommendations` в расписании celery beat, раз в сутки:
подбирает несколько треков по вкусу и докачивает их в хранилище через
WARP. Утром они уже в медиатеке и играют офлайн.

Лимит по умолчанию скромный (5 треков): смысл в том, чтобы медиатека
росла понемногу каждый день, а не чтобы за ночь залить тысячу случайных.

Отказ на одном треке (возрастное ограничение, удалённый ролик) не
останавливает задачу — она идёт дальше.

Заодно из расписания убрана `cleanup_orphaned_avatars`: она была
прописана, но самой задачи в `tasks.py` нет — beat спотыкался бы
на ней при каждом запуске.

## Скорость

| что | было | стало |
|---|---|---|
| ссылка на поток, повторно | 1.48 с | **0.3 с** |
| импорт трека | 9.3 с | **4.7 с** |
| прогрев очереди | 2 трека, по очереди | **4 трека, параллельно** |

**Кэш ссылок.** Извлечение занимает секунду-полторы, а ссылка живёт часами —
держим её в Redis. Срок берём из самой ссылки: у неё в параметрах записано
`expire`, вычитаем 10 минут про запас. Угадывать нельзя — отдадим просроченную,
и воспроизведение упадёт на середине очереди.

**Импорт без перекодирования.** Прогон через ffmpeg в mp3 192k был самой
долгой частью, и качество от второго сжатия только падало. Теперь m4a
как есть — играет нативно на обеих платформах.

**Прогрев очереди** (`queueStore.ts`). Было два трека и последовательный
обход: четыре трека по полторы секунды — это шесть секунд с пустой очередью.
Теперь четыре, и ссылки запрашиваются параллельно, а в движок добавляются
строго по порядку — иначе очередь бы перемешалась.

## Чего это не решает

Прослушивание по требованию с ютуба на сервере по-прежнему не работает
(`502`, см. `docs/youtube-block.md`). И не заработает без резидентного адреса.

Но при этой схеме оно почти не нужно: всё, что тебе нравится, оказывается
в R2 и играет оттуда — быстрее, офлайн и без зависимости от того, что
случится с роликом на ютубе.
