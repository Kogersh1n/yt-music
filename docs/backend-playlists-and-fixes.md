# Плейлисты и доводка бэкенда

Дата: 2026-08-28 · ветка `main` · `backend/app/src`

Дописан модуль плейлистов и закрыты оставшиеся хвосты: лайки, поиск
по медиатеке, `/users/me`, logout. Итого 33 ручки, приложение импортируется
целиком, мапперы SQLAlchemy конфигурируются.

---

## 1. Модуль плейлистов

Раньше: `models.py` и `schemas.py` были, `router.py` и `service.py` — по 0 байт,
репозитория не было вовсе.

### `schemas.py` — переписан

Главная правка: `user_id: int` при том, что во всём проекте UUID. Такой ответ
не прошёл бы валидацию ни разу.

Ответов теперь два, и это осознанно:

| схема | когда |
|---|---|
| `PlaylistResponse` | список «мои плейлисты» — без треков, но со `songs_count` |
| `PlaylistDetailResponse` | экран одного плейлиста — с треками |

Если бы схема была одна, список из десяти плейлистов тянул бы всю медиатеку
ради четырёх названий на экране.

### `repository.py` — новый

- `list_for_user` — плейлисты со счётчиком треков. Счёт отдельной колонкой
  через `scalar_subquery`, а не длиной подгруженного списка.
- `get_for_user` — плейлист с треками (`selectinload`). **`user_id` стоит
  в `WHERE`, а не проверкой после выборки** — чужой плейлист должен быть
  неотличим от несуществующего, иначе по коду ответа можно перебрать чужие id.
- `has_song`, `add_song`, `remove_song` — работа с таблицей связи напрямую.
- `recalc` — пересчитывает длительность и число треков одним запросом.

Про `recalc` стоит сказать отдельно. Можно было прибавлять и вычитать
длительность при каждом изменении — дешевле на один запрос. Но накопленная
ошибка после любого сбоя посередине уже ничем не лечится: правильного значения
взять неоткуда. Пересчёт всегда даёт верную цифру.

### `service.py` — новый

`_require_own` — единая точка проверки владельца, через неё проходят все
операции. Возвращает `NotFoundError`, а не `ForbiddenError`: 403 подтвердил бы,
что по этому id что-то существует.

`_summary` — сборка краткого ответа. Тут был мой собственный баг, который
я нашёл до конца работы: `PlaylistResponse.model_validate(playlist)` молча
подставлял `songs_count = 0`, потому что у ORM-объекта такого поля нет,
а у схемы есть значение по умолчанию. Теперь счётчик считается явно везде —
и при создании, и при переименовании, и при добавлении трека.

### `router.py` — новый

```
GET    /playlists/                          мои плейлисты
POST   /playlists/                          создать
GET    /playlists/{id}                      плейлист с треками
PATCH  /playlists/{id}                      переименовать
DELETE /playlists/{id}                      удалить
POST   /playlists/{id}/songs/{song_id}      добавить трек
DELETE /playlists/{id}/songs/{song_id}      убрать трек
```

Все — под `UserDep`. Плейлист без владельца не имеет смысла.

Удаление плейлиста сносит только связи (`ondelete=CASCADE` на `playlist_song`),
сами треки остаются в медиатеке.

Роутер подключён в `main.py`.

## 2. Лайки — были не дописаны

`add_like` в `songs/service.py` обрывался на `NotFoundError`: находил песню
и ничего не делал. При этом мобильное приложение уже показывает лайки —
и хранит их локально, потому что серверных не было (см. `mobile/src/local/likes.ts`).

### `SongRepository` — четыре метода

`add_like` сделан через `INSERT ... ON CONFLICT DO NOTHING`, а не
«проверить и вставить»:

```python
stmt = (
    pg_insert(liked_songs)
    .values(user_id=user_id, song_id=song_id)
    .on_conflict_do_nothing()
)
```

Два быстрых нажатия подряд иначе гонятся за одну строку, и второе падает
нарушением первичного ключа. Счётчик `Song.liked` двигается **только при
реальной вставке** (`rowcount != 0`) — иначе он разъехался бы с числом строк
связи после первого же двойного тапа.

`remove_like` симметрично, с `greatest(liked - 1, 0)`: счётчик не должен уйти
в минус, если история и счётчик когда-то разошлись.

`liked_ids` возвращает множество id одним запросом — чтобы список песен
не делал по запросу на строку.

### Ручки

```
POST   /songs/{id}/like     поставить
DELETE /songs/{id}/like     снять
GET    /songs/liked         мои лайки
```

Обе операции идемпотентны: повтор не ошибка. Для клиента «уже стояло»
неотличимо от «поставили» — так проще писать оптимистичный UI.

## 3. `/songs/search` искал не там

Было: ручка объявлена как `response_model=list[SongResponse]`, а сервис звал
`search_youtube` и возвращал `{results, query}`. Ответ не проходил валидацию —
**эндпоинт падал всегда**. Мобильное приложение это уже обнаружило и обходило,
там прямо в комментарии написано «намеренно НЕ используем `/songs/search`».

Стало — два разных поиска:

| ручка | где ищет |
|---|---|
| `GET /songs/search` | своя медиатека, по названию и исполнителю |
| `GET /songs/youtube/search` | ютуб |

В репозитории метод `search` уже был написан и не использовался — теперь он
подключён. Метод сервиса `search_songs` переименован в `search_youtube_songs`,
чтобы имя не обещало поиск по своим трекам.

## 4. `/users/me`

Была заглушка `raise HTTPException(501)`. Теперь возвращает `UserResponse`
прямо из `UserDep`: `get_current_user` уже сходил в базу и проверил, что
пользователь существует и подтверждён — второй запрос был бы лишним.

Файл роутера заодно почищен от неиспользуемых импортов (`UUID`, `AsyncSession`,
`Depends`, `HTTPException`, `get_async_session`, `user_service`).

---

## 5. `users/service.create_user` удалён

Метод был сломан в трёх местах сразу: `User(**dict)` получал ключ `password`,
которого нет в модели; `new_user.password_hash` — такого поля тоже нет
(в модели `hashed_password`); и он делал свой `session.commit()` в обход
общей транзакции.

Чинить его было незачем — регистрация целиком живёт в `auth.verify_user`.
Удалён вместе с осиротевшими импортами.

Заодно в том же файле: `get_by_email(session, email)` вызывался позиционно,
а в репозитории аргумент keyword-only — `TypeError` при каждом вызове.

## 6. Logout не совпадал с сервисом

Сервис принимает `raw_token`, роутер передавал `access_token_str=` и
`refresh_token_str=` — `TypeError` на каждом запросе.

Приведено к сигнатуре сервиса. Заодно убран `TokenDep`:

- blocklist для access-токенов не заведён, так что access доживает свои
  15 минут в любом случае — требовать его нечего;
- без него исчезает проблема «протух access — не могу выйти».

Ответ теперь `204`, ошибка не возвращается: выход идемпотентен, и «токена
не было» для клиента неотличимо от «вышли успешно».

## Требует твоего внимания

### Пропала миграция

В базе стоит ревизия `8a2c450a3297`, **а файла для неё в `alembic/versions/`
нет**. В репозитории только `514c9d36b3ee_initial_migration.py`, и он создаёт
лишь `song` и `user`.

То есть таблицы `playlist`, `playlist_song`, `liked_songs` и `refresh_token`
существуют в твоей локальной базе, но **не воспроизводятся из репозитория**.
На чистой машине `alembic upgrade head` создаст две таблицы из семи, а `upgrade`
на существующей базе упадёт с «Can't locate revision identified by 8a2c450a3297».

Похоже, ревизия генерировалась внутри контейнера и не попала на хост.

Чинится легко, потому что **все таблицы пустые — 0 строк**:

```
docker-compose down -v          # снести том postgres
docker-compose up -d db
docker-compose run --rm web alembic upgrade head          # song + user
docker-compose run --rm web alembic revision --autogenerate -m "playlists, likes, refresh tokens"
docker-compose run --rm web alembic upgrade head
```

Сгенерированный файл окажется на хосте, если `backend/` смонтирован; если нет —
скопируй его из контейнера. Сам я миграцию сгенерировать не смог: alembic
на хосте не установлен (в `requirements.txt` он есть, но ставится в образе).

### Схема БД сейчас совпадает с моделями

Проверил `refresh_token` напрямую — `family_id`, `token_hash`, `revoked_at`,
`replaced_with_id` на месте. Так что после пересоздания тома автогенерация
даст ровно то, что нужно, без сюрпризов.

### Лайки на мобилке всё ещё локальные

`mobile/src/local/likes.ts` хранит их на устройстве и в комментарии обещает
переключиться, «когда появится auth и `/me/likes`». Серверные лайки теперь
есть — ручки `POST/DELETE /songs/{id}/like` и `GET /songs/liked`. Переключение
трогает только этот файл, как там и написано.

### Что осталось по плану

Этапы 10–11 из плана ротации: отзыв всех сессий при смене пароля
(`revoke_all_for_user` в репозитории уже написан), celery-задача на уборку
протухших токенов, rate limit на `/login` и `/refresh`.
